# Data Dictionary and Relationship Guide

This document describes the synthetic datasets and their principal relationships. The generated CSV headers and the source modules are the authoritative definitions of exact field names and types; this guide intentionally avoids inventing column names that have not been independently checked here.

## 1. Master Data Entities

| Entity / dataset | Purpose | Recorded baseline |
|---|---|---:|
| `plants.csv` | Synthetic plant/facility records. | 3 |
| `production_lines.csv` | Production lines associated with plants. | 12 |
| `machines.csv` | Equipment records assigned to production lines. | 100 |
| `sensors.csv` | Sensors associated with machines. | 500 |
| `operating_shifts.csv` | Operating shift definitions/context. | 3 |
| `technicians.csv` | Synthetic maintenance technician records. | 20 |
| `parts.csv` | Synthetic parts catalogue. | 10 |

## 2. Operational Event Datasets

| Dataset | Purpose | Recorded baseline |
|---|---|---:|

| `telemetry_enriched.csv` | Telemetry enriched with associated machine/operating context. | Generated by the pipeline; see CSV output. |

## 3. Identifiers and Recorded Entity Types

The recorded machine identifier pattern is `MCH-<line-id>-001`. Machine types in the generated baseline include `COMPRESSOR`, `CONVEYOR`, `MOTOR`, and `PUMP`; baseline machine status is `ACTIVE`.

The recorded sensor identifier pattern is `SNS-<machine-id>-<sensor-type>-01`. Sensor types include `CURRENT`, `PRESSURE`, `SPEED`, `TEMP`, and `VIBRATION`. Recorded unit values include `A`, `C`, `bar`, `mm/s`, and `rpm`.

Exact column types and any additional enum values should be checked against the generated CSV headers and generator source before changing this reference.

## 4. Principal Relationships

- Plant → ProductionLine: one-to-many.
- ProductionLine → Machine: one-to-many.
- Machine → Sensor: one-to-many.
- Sensor → TelemetryEvent: one-to-many.
- Machine → FailureEvent: one-to-many.
- FailureEvent → MaintenanceWorkOrder: one-to-one in the generated baseline.
- Technician → MaintenanceWorkOrder: one-to-many.
- MaintenanceWorkOrder → Part: many-to-many through `work_order_parts.csv`.

## 5. Maintenance Time Fields

Two duration measures are maintained:

- `repair_duration_hours` = maintenance completion timestamp minus maintenance start timestamp.
- `downtime_hours` = maintenance completion timestamp minus failure timestamp.

For the synthetic data, downtime is assumed to begin at failure occurrence and end at maintenance completion. It is a derived synthetic estimate and must not be described as measured production downtime.

## 6. Maintenance Status History

`maintenance_status_history.csv` stores the following status transitions for each baseline work order:

1. `NONE` → `OPENED`
2. `OPENED` → `IN_PROGRESS`
3. `IN_PROGRESS` → `COMPLETED`

The baseline contains 450 lifecycle records for 150 work orders. The event history is separate from the current status fields on the work-order records. This project does not claim to implement broader plant or machine status-history event streams.

## 7. Risk and Evaluation Outputs

| Output | Purpose |
|---|---|
| `machine_risk_scores.csv` | Current machine-level risk score, band, components, reasons, data-quality indicators, and recommendation. |
| `risk_audit_log.csv` | Traceable record of scoring version, machine, input window, score/band, reasons, and recommendation. |
| `risk_evaluation_predictions.csv` | Historical machine-day decisions and evaluation outcomes. |
| `risk_evaluation_metrics.csv` | Aggregated risk-evaluation metrics. |

The risk engine uses recent 24-hour telemetry, sensor-specific thresholds/trends, maintenance activity over the previous 30 days, and operating context. Ground-truth labels are not input features. Risk scores are heuristic indicators, not calibrated failure probabilities.

## 8. Exports

`src/export_data.py` exports 12 relational datasets to JSON and SQLite and generates a SQL schema/seed dump. High-volume telemetry remains in CSV form. Recorded checks confirmed JSON/SQLite row-count agreement and no SQLite foreign-key violations. The SQL seed was generated, but a fresh-database replay is not recorded as tested.
